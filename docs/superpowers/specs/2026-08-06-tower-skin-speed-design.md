# 타워 외형이 생산속도를 정한다 — 설계

작성: 2026-08-06

## 무엇을 만드는가

타워 외형을 상점에서 팔고, **산 외형이 그 사람의 생산속도를 정한다.** 유닛 종류가
이미 같은 구조다 (`units.ts`: 종류가 `power` 를 정한다) — 그 구조를 타워로 옮긴다.

없앤 것은 이미 없앴다: 추상적인 단계 강화 `speedLevel` 은 `de94851` 에서 통째로
제거했다 (HANDOFF §-73). `PlayerMods.speedMul` 배관만 1.0 으로 남아 있고, 이 작업이
그 자리에 값을 넣는다.

### 왜 외형인가

`speedLevel` 은 숫자만 오르고 화면에 아무것도 안 나타났다. 외형에 붙이면 **산 것이
판에서 보이고**, 상한이 생겨(외형 개수) 과금 격차가 무한히 벌어지지 않는다.
유닛에서 이미 통한 방식이다.

## 카탈로그

| 종류 | 그림 | `speed` | 가격 |
|---|---|---|---|
| 종류 | 그림 | `speed` | 가격 |
|---|---|---|---|
| `tower_hut` | `lv1` 오두막 | 1.00 | 0 (기본) |
| `tower_keep` | `lv4` 석탑 | 1.25 | 400 |
| `tower_house` | `lv2` 집 | 1.50 | 900 |
| `tower_barracks` | `lv3` 병영 | 1.75 | 1500 |
| `tower_citadel` | `lv5` 성채 | 2.00 | 2400 |
| `tower_prime` | `lv5` + 왕관·아우라 | 2.50 | VX 전용 |

**`lv` 번호 순이 아니다** (2026-08-07에 바꿨다). 처음엔 옛 레벨 사다리를 그대로 썼는데
실물에서 **석탑(`lv4`)이 병영(`lv3`) 뒤에 오니 약해 보였다** — 석탑은 높지만 좁고,
병영은 넓어서 화면에서 더 크게 읽힌다. 석탑을 두 번째로 올렸다.

**이름과 그림은 안 옮겼다.** 옮긴 것은 `price` 와 `speed` 뿐이다 — 사다리의 자리는 그
두 값이 정하고, `SPEED_ORDER`·`towerTierOf`·`stepDownTower` 가 전부 `speed` 에서
파생되므로 봇 보정과 등급 표시가 저절로 따라온다.

**새 에셋이 필요 없다.** `game/public/assets/tower/{p1,p2,neutral}/lv1~lv5.png` 가
그대로 있다 — 옛 타워 레벨 사다리(2026-07-30에 레벨을 없애면서 `lv3` 하나만 쓰게
됐다)를 되살려 쓰는 것이다. 그림 자체가 이미 "셀수록 세 보이는" 사다리다.

`tower_prime` 은 그림이 없으니 `lv5` 를 빌려 쓰고 아우라로 구분한다 — 유닛의
`beergang_rainbow` 와 같은 처리(`spriteKindOf`).

가격은 유닛 표(`UNIT_PRICES`)를 그대로 빌렸다. 두 축의 체감 가격이 같아야
"무엇을 먼저 살까"가 순수한 취향 문제가 된다.

### 중립 타워는 `lv1` 로 내린다

지금은 중립도 `lv3`(병영)이다. 그대로 두면 **무과금 플레이어의 타워(작은 집)가 주인
없는 타워보다 초라해 보인다.** 중립을 가장 낮은 `lv1` 로 두면 점령이 "건물이
올라간다"로 읽힌다.

순수 시각 변경이다 — 타워 반경도 규칙도 안 건드린다.

### 어느 타워에 입히는가

**소유자의 종류로 그린다.** 내 타워는 전부 내 외형, 상대 타워는 전부 상대 외형, 주인
없는 것만 `lv1`. 점령하면 그 자리에서 내 외형으로 바뀐다 — 판이 진행될수록 내 성이
늘어나는 것이 곧 이기고 있다는 신호가 된다.

생산속도가 내 타워 **전부**에 걸리므로 그림도 전부 바뀌어야 "외형 = 성능"이 거짓말이
안 된다 (사용자 결정).

### 사면 바로 착용한다

유닛(`buyUnitKind`)과 같다. 산 직후에 또 한 번 눌러야 입는 구조면 "샀는데 왜 그대로지"가
된다. 이미 가진 것을 누르면 착용만 바뀐다.

### 그림 크기는 종류별로 안 바꾼다

유닛은 `sizeFactorOf` 로 센 것을 크게 그리지만 **타워는 그러면 안 된다.** 타워 반경은
병력 수가 정하고 **그것이 게임 규칙이다** — 경로가 그 원에 걸리면 개설할 수 없다
(`sim/config.ts` 의 `towerRadiusOf`). 성채라고 크게 그리면 그림과 판정이 어긋나
"왜 여기 경로가 안 그어지지"가 된다.

집 → 성채라는 실루엣 차이만으로 충분하다.

## 데이터 흐름

```
서버 계정 (towerKind)
  → setReady 가 방 players 에 싣는다
  → #start 가 towerKinds[slot] 으로 방 상태에 박는다
  → RoomSnapshot.towerKinds → MatchSetup.towerKinds
  → MatchScene.restart: speedMul: towerSpeedOf(towerKinds[n])
  → PlayerMods.speedMul → sim
```

### 지켜야 할 규칙 (전부 유닛에서 이미 정한 것)

1. **서버는 이름만 내려준다.** 이름 → 배수 변환(`towerSpeedOf`)은 클라이언트에만 둔다.
   공식을 양쪽에 복사하면 언젠가 어긋나고, 어긋나는 순간 두 클라이언트가 다른 판을 돈다
2. **각자 자기 계정을 읽으면 안 된다.** 서버가 정한 값을 양쪽이 똑같이 읽어야 첫 틱부터
   안 갈라진다. 클라이언트가 값을 보내게 두면 안 산 외형의 속도를 자칭할 수 있다
3. **`sim/` 은 `towers.ts` 를 모른다.** 숫자만 `PlayerMods.speedMul` 로 건네받는다 —
   시뮬레이션이 카탈로그를 알면 서버에서 같은 코드를 못 돌린다
4. **모르는 종류는 던지지 말고 기본값으로 떨어뜨린다.** 배포 시점이 어긋난 클라이언트가
   새 종류를 들고 들어오는 일이 실제로 있다 (`agent8.ts` 의 `toKind` 주석). 양쪽이
   똑같이 기본값으로 보면 갈라지지 않는다

### 스프라이트 로딩

지금은 타워 3장(`p1`/`p2`/`neutral` 의 `lv3`)을 미리 받는다. 종류가 생기면 11장이 되는데
**한 판에 실제로 쓰이는 건 3장뿐**이다 (내 종류·상대 종류·중립). 아바타(`Profiles`)가
하는 것처럼 판이 시작될 때 필요한 것만 받는다.

### 저장본 이행

스키마를 10 → 11 로 올린다. 옛 저장본에는 `towerKind` 가 없으므로 기본값
(`tower_hut`)으로 떨어진다. 서버 계정도 같다 — `normalizeAccount` 가 없는 필드를
기본값으로 채운다. **이행 코드가 따로 필요 없다**(잃을 것이 없는 새 필드다).

### 외부 의존

`tower_prime` 은 VX 상품이라 Verse8 CrossRamp 에 항목을 올려야 실제로 팔린다
(`net/vx.ts` 의 `PremiumItem`). 그 전까지는 상점에 "준비 중"으로 뜬다 —
배속(`tempo_boost`)이 지금 그 상태다.

## 봇 보정

```
봇 타워 = stepDownTower(내 타워)
```

유닛(`stepDownKind`)과 같은 규칙이다. **다만 바닥이 필요하다** — 기본 타워
(`tower_hut`)를 쓰면 아래가 없어 봇이 사람과 동등해지고, `difficulty.ts` 의 실측표
기준 사람 승률이 40%로 떨어진다. 신규가 가장 많이 겪을 상태인데 거기서 가장 어려워진다.

그래서 기본 타워일 때만 `BOT_SPEED_MUL`(= 0.98, `de94851` 에서 넣어 둔 값)을 쓴다.

| 내 타워 | 봇 속도 | 차이 |
|---|---|---|
| hut (1.00) | 0.98 (바닥) | −2% |
| house (1.25) | 1.00 | −20% |
| barracks (1.50) | 1.25 | −16.7% |
| keep (1.75) | 1.50 | −14.3% |
| citadel (2.00) | 1.75 | −12.5% |
| prime (2.50) | 2.00 | −20% |

**봇 타워 그림도 같이 내린다.** 유닛이 그림과 힘을 같은 함수(`stepDownKind`)에서
뽑는 것과 같은 이유 — 어긋나면 화면이 거짓말을 한다.

## 알고 넘어가는 것

### 밸런스 절벽

단계당 +0.25배는 지금(4%)의 6배다. `units.ts` 의 실측은 유닛 `power` 5% 차이가
승률 93%였다 — 기전은 다르지만 누적 이득이라는 성질은 같다. 봇 "한 단계 아래" 규칙과
곱해지면 봇전이 한쪽으로 쏠릴 수 있다:

- 기본 타워: 봇과 −2% 차이 → 어렵다
- 한 단계만 사면: −20% 차이 → 거의 안 진다

**사용자 결정으로 일단 이 값으로 넣고 직접 플레이해 조정한다.** 그래서 조정이 한 곳에서
되게 만든다 — `TOWER_KIND_META` 의 `speed` 값만 고치면 서버·봇·상점 표시가 전부 따라온다.

### 배포 과도기의 데싱크

옛 클라이언트는 `towerKinds` 를 몰라 `speedMul 1.0` 으로 돌고, 새 클라이언트는 2.0 으로
돈다. 그 둘이 붙으면 첫 틱부터 갈라진다.

**배포 순서로는 못 막는다** — 어느 쪽을 먼저 올려도 과도기엔 섞인다. 유닛 종류를 추가할
때 이미 감수한 위험이고(`agent8.ts` 의 `toKind` 주석), 완화 수단도 이미 있다: 서버가
상태 해시를 비교해 데싱크를 `desync` 필드에 기록한다. 실제로 섞이는 창은 배포 직후
몇 분이고, 웹이라 새로고침하면 최신을 받는다.

## 안 하는 것

- **기존 `speedLevel` 구매 이행** — 정식 출시 전이라 안 챙긴다 (사용자 결정)
- **외형별 타워 크기 차이** — 반경이 게임 규칙이라 그림만 바꾼다 (위 참고)
- **외형을 타워마다 따로 고르기** — 계정에 하나, 내 타워 전부에 입힌다 (사용자 결정)
